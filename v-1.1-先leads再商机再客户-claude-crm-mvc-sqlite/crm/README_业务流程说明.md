# CRM 业务流程说明

## 核心业务流程

```
┌─────────────────────────────────────────────────────────────────┐
│                         线索生命周期                              │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
                     ┌─────────────────┐
                     │  新建线索 (new)  │
                     │  陌生客户信息    │
                     └────────┬────────┘
                              │
                              ▼
                     ┌─────────────────┐
                     │ 已联系(contacted)│
                     │ 初步沟通了解需求  │
                     └────────┬────────┘
                              │
            ┌─────────────────┼─────────────────┐
            │                 │                 │
            ▼                 ▼                 ▼
   ┌───────────────┐  ┌───────────────┐  ┌───────────────┐
   │ 有真实采购意向 │  │ 只是比价/暂无 │  │  符合流失条件 │
   │ 采购时间明确   │  │ 真实采购意愿   │  │              │
   │ 采购数量确定   │  │              │  │              │
   └───────┬───────┘  └───────┬───────┘  └───────┬───────┘
           │                  │                  │
           ▼                  ▼                  ▼
   ┌───────────────┐  ┌───────────────┐  ┌───────────────┐
   │   转为商机     │  │  持续跟进     │  │  标记流失     │
   │  (qualified)  │  │  (contacted)  │  │   (lost)     │
   └───────┬───────┘  └───────────────┘  └───────┬───────┘
           │                                      │
           ▼                                      ▼
   ┌───────────────┐                      ┌───────────────┐
   │ 自动创建客户  │                      │ 记录流失原因  │

   └───────────────┘                      └───────────────┘
```

线索确认 → 自动创建客户 + 商机后，进入 **商机生命周期**（见下）。

## 线索状态说明

| 状态 | 含义 | 操作 |
|------|------|------|
| `new` | 新建线索，尚未联系 | 编辑、删除 |
| `contacted` | 已联系，初步沟通中 | 转商机、标记流失、编辑 |
| `qualified` | 已确认有真实意向，已转为商机 | 查看（只读） |
| `lost` | 流失，暂无机会 | 重新激活 |

> **列表列说明**：`流失原因` 仅在顶部筛选为“**已流失**”时才作为一列出现；
> 全部 / 新建 / 已联系 / 已确认四个标签页不展示该列（否则该列全为“—”，干扰阅读）。

## 流失原因列表

标记流失时必选一项；已流失线索的流失原因在“已流失”标签页的`流失原因`列展示。

| 原因代码 | 说明 |
|----------|------|
| `no_need` | 暂无需求 |
| `competitor` | 已选竞品 |
| `budget` | 预算不足 |
| `no_match` | 需求不匹配 |
| `no_response` | 长期无响应（超过30天） |
| `project_cancel` | 项目取消 |
| `contact_lost` | 联系不上 |
| `other` | 其他原因 |

## 商机生命周期（看板流转规则）

商机在**看板**上按阶段流转，看板只保留 4 列：`进行中` → `方案阶段` → `谈判中` → `成交`。

| 阶段 | 含义 | 终态行为 |
|------|------|----------|
| `open` | 进行中，初步接触 | — |
| `proposal` | 方案阶段，已提交方案或报价 | — |
| `negotiation` | 谈判中，议价或审批 | — |
| `closed_won` | 成交 | **自动创建订单**；商机**不归档**，保留在"成交"列供查阅 |
| `closed_lost` | 丢单 | **自动归档**，移出看板 |

规则要点：
1. **成交（closed_won）**：编辑商机把阶段改为"成交" → 系统自动生成订单（可先填商品明细，订单金额=明细合计，附件自动继承）→ 商机**保留在看板"成交"列**，不会归档。
2. **丢单（closed_lost）**：把阶段改为"丢单" → 商机**自动归档**，从看板移除。
3. **恢复**：在"已归档"页点击"恢复" → 商机取消归档，并**重置回"进行中"(open)**，可重新跟进。
4. 看板**没有"丢单"列**；丢单商机只存在于归档列表。

## 订单流转

```
商机成交 → 自动创建订单(pending) → 确认 → 处理 → 发货 → 送达 → 完成
                                                  ↘ 取消
```

| 订单状态 | 说明 |
|----------|------|
| `pending` | 待确认 |
| `confirmed` | 已确认 |
| `processing` | 处理中 |
| `shipped` | 已发货 |
| `delivered` | 已送达 |
| `completed` | 已完成 |
| `cancelled` | 已取消 |

付款状态：`unpaid`（未付款）→ `partial`（部分付款）→ `paid`（已付款）

## 商机 vs 线索 vs 跟进记录

| 类型 | 定义 | 特点 | 存在位置 |
|------|------|------|----------|
| **商机** | 有真实采购意向的询价 | 有采购时间、意愿、数量 | 商机看板 |
| **线索** | 潜在客户信息 | 尚未转化为客户 | 线索列表 |
| **跟进记录** | 比价或无采购意愿的询价 | 记录客户比价情况 | 客户详情页 |

## 数据流转

### 1. 线索转商机
```
线索 → 点击"转为商机" → 自动创建客户 → 自动创建商机 → 线索状态变为qualified
```

### 2. 线索流失
```
线索 → 点击"标记流失" → 选择流失原因 → 线索状态变为lost
```

### 3. 流失重新激活
```
已流失线索 → 点击"重新激活" → 线索状态恢复为contacted → 可继续跟进或转商机
```

### 4. 商机成交
```
编辑商机(阶段=成交) → 系统自动创建订单 → 商机保留在看板"成交"列
```

### 5. 商机丢单与恢复
```
编辑商机(阶段=丢单) → 商机自动归档(移出看板)
归档列表 → 点击"恢复" → 商机回到"进行中"列，重新跟进
```

### 6. 个人信息与负责人同步
```
设置 → 个人信息（改名 / 换手机 / 填职位） → 只写 users 表
→ 客户 / 线索 / 商机 / 订单的“负责人”读取时 JOIN users → 立即显示新信息
```
各业务表只存 `owner_id`（跟进存 `user_id`、附件存 `uploaded_by`），不存姓名副本，
因此无需“同步按钮”；设置页的**信息同步范围**面板会列出当前账号被引用的记录数。

### 7. AI 辅助操作（可选，默认关闭）
```
设置 → AI 助手（管理员启用、选服务商/模型/Key）

AI 助手共 21 个工具，分三档权限（`Ai::tools()` 是唯一真相，文档与提示词都仍生成自它）：

| 档 | 工具 | 什么时候写库 |
| --- | --- | --- |
| 查询 | `search_records`、`get_record`、`get_settings` | **从不**。生成计划时就执行完并直接显示结果；可搜索范围是 `Ai::searchSurfaces()` 白名单，`app_settings` 与 `users` 不在内，所以 API Key、密码散列拿不到。`get_settings` 只读设置，密钥永远只回“已配置，不回显”。`search_records` 除关键词 `q` 外还支持条件 `country`（**中英都认**：库里 `印度` 与 `United States` 混写也能命中）/ `status` / `stage` / `owner`（填负责人姓名），`q` 与条件至少要给一个；要整表须显式 `all:true`（用户说“所有/全部”时）。结果带<strong>精确总数</strong>，「现在有多少客户」可一句答准 |
| 写入 | `create_lead/customer/deal`、`add_follow_up`、`update_lead/customer/deal/order/follow_up`、`update_lead_status`、`update_deal_stage`、`set_order_items`、`update_setting` | 预览确认模式下点“确认执行”才写（自动执行模式下直接写）。**字段覆盖 = 表结构**：`Ai::fieldsFor()` 由 `Schema::columns()` 生成参数，线索 22 项 / 客户 19 项 / 订单 11 项 / 商机 7 项 / 跟进 6 项，库里加一列 AI 就能写一列。只改你点名的字段，传空串即清空（NOT NULL 列拒绝清空）；`status=lost` / `stage` / `archived` 会连带写时间戳（与人工操作同语义）；`update_setting` 仅管理员且密钥项不可改。别人负责的行整条拒绝 |
| 先查再做 | `Ai::complete()` 是最多 3 轮的循环：模型只给条件（“印度的所有客户”）时，第一轮它只能发查询，系统当场执行（只读）并把真实编号用 `<tool_results>` 回灌，第二轮它才对那些编号出写/删计划。所以「删除印度所有客户」「删掉名字含 armtek 的客户及其线索/商机/订单」是可执行的；一个计划最多删 20 条，超出整批拒绝 |
| 引用方式 | 每条记录带**稳定编号**：客户 `CUS-000007`、线索 `LEAD-000007`、商机 `DEAL-000007`（`public_code` 列，新增时由 `Model::publicCode()` 按 id 派生，不可手工指定、不可被改），订单用 `order_number`。所有 `*_id` 参数编号与数字 ID 都收，编不出来的编号会被拒而不是误伤 |
| 护栏 | ≥2 个删除动作必须“本轮真查过库”或用户点名编号才允许出计划（`BULK_DELETE_NEEDS_QUERY`）；删除预览显示每条的国家/状态/阶段/收款/公司与连带数量，供人核对 | 
| 删除 | `delete_lead/deal/order/customer`、`delete_ai_request` | **只有人工“确认执行”**。强制 `confirm:true` + 理由，预览直接显示连带影响（多少线索/商机/订单/附件），开了自动执行也不跳确认；被删内容留快照在 `ai_actions`；总开关 `ai_allow_delete` 可整个关掉 |

AI 删客户的级联与页面一致：名下线索/商机/订单一并删除，`attachments` 行与磁盘文件一并清理（这一项比页面做得更多，页面删不会清文件）；删商机只把订单的 `deal_id` 置空，不删订单。
→ /ai 粘贴邮件/WhatsApp/会议记录 → 模型返回“操作计划”JSON
→ 服务端校验（工具白名单 + 参数 + 记录归属与权限）
→ 【预览确认】人点“确认执行” → 写库；或【自动执行】直接写库
→ 全过程写入 ai_actions 审计（谁、原始指令、计划、结果、模型、耗时）
```
AI 能做的事已经覆盖线索/客户/商机/订单/跟进的全部字段与（仅限管理员的）系统设置；
**仍然不能**：改编号与单号（`public_code`、`order_number`）、改他人与密钥、改账号资料（去 设置→个人信息）、
以及时刻表——`created_at/updated_at/lost_at/archived_at/stage_*_at` 这类时间列只能由系统带出（见 `Ai::PROTECTED_COLUMNS`）。
所有写操作依旧受白名单与归属权限约束（沿用销售权限规则）。

### 8. 应用信息（仅管理员）
```
设置 → 应用信息（系统名称 / 副标题 / 公司名称 / 货币符号）
→ 写入 app_settings 键值表 → appSetting() / appName() / money() 读取 → 全站即时生效
```
可逐项或一次性恢复为代码默认值（默认值定义在 `app/models/Setting.php`）。

## 设置与个人信息同步

| 位置 | 谁可改 | 内容 | 生效范围 |
|------|--------|------|----------|
| 设置 → 个人信息 | 本人 | 姓名、邮箱（登录账号）、职位、电话、WhatsApp、备注 | 全局：客户/线索/商机/订单的**负责人**、跟进与动态的**记录人/操作人**、附件**上传人**、顶栏用户名 |
| 设置 → 修改密码 | 本人 | 当前密码 + 新密码（≥ 6 位） | 下次登录 |
| 设置 → 应用信息 | 仅管理员 | 系统名称、系统副标题、公司名称、版权信息、货币符号 | 全站页面（侧边栏、标题、登录页、所有金额） |
| 设置 → AI 助手 | 仅管理员 | 启用开关、服务商、模型、接口地址、API Key（掩码）、执行方式、快速模式、响应超时、最大回复长度、**允许 AI 删除数据**、temperature | AI 助手能力与归属 |

实现要点：
1. **人的信息只存一份**：`users` 是唯一来源，其他表只存 `users.id`，读取时 JOIN 回姓名；
   没有“姓名副本”需要维护，也不会出现改了一个地方、另一个地方仍旧的情况。
2. **应用信息存 `app_settings`**（键值表），每请求只读一次（静态缓存），表格缺失时自动退回默认值，
   因此未执行迁移也不会报错。`config.php` 里的 `APP_NAME` 仅作默认值，`APP_VERSION` 仍由代码控制。
3. 销售账号看不到、也提交不了“应用信息”表单（`requireRole('admin')`）。

## 数据库初始化

数据库统一由 `database/migrate.php` 管理（SQLite）：

```bash
php database/migrate.php          # 创建/修复/升级数据库（幂等，可重复执行）
php database/migrate.php --status # 查看迁移状态
```

- `database/schema.sql` 是唯一权威的完整结构 + 种子数据（幂等自愈）。
- 对已有表的结构性变更（ALTER 等）放在 `database/migrations/NNN_*.sql`，只执行一次。
  若基线已含该列（全新库场景），纯加列的增量会输出 `skipped: …` 并直接登记，
  不会报 `duplicate column name`；旧库缺列时仍会正常执行。
